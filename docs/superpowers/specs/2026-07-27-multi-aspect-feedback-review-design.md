# 多主题评论与人工复核设计

## 目标

让一条长评论最多关联两个既有主题，并为每个主题独立给出正面、负面或中性情绪；仅把规则无法可靠判定的少量评论放入人工复核候选队列。

## 边界与取舍

- 保留 `issue_catalog` 与既有 `feedback_issue_link` 的主题键、趋势和告警口径，不重算历史投影。
- 一个反馈事件最多写入两个主题关联；超过两个规则候选、并列歧义、无主题命中和混合情绪才生成候选。
- 情绪使用可解释的关键词规则，不为该能力新增模型调用或外部数据源。
- 候选仅保存反馈事件内部 ID、受控原因、推荐主题键和情绪，不保存模型思维链；原评论仍沿用既有脱敏存储边界。
- 人工操作只允许确认建议、忽略候选，或提交“新主题候选”；不得直接改写规则、历史链接或指标。
- 所有查询和写入以 `workspace_id` 隔离，外部接口仅使用候选与 Workspace 的 `public_id`。

## 数据与流程

1. 规则分类器按原有优先级输出最多两个主题；同时报告候选总数是否超过上限和是否并列。
2. 主题情绪分析器在评论文本中按主题相关词附近的正负面词给出 `positive`、`negative`、`neutral` 或 `mixed`。
3. 投影写入原有 `feedback_issue_link`，并新增每个主题关联的情绪事实。`mixed` 不进入单一情绪统计。
4. 投影根据受控原因创建一条幂等的复核候选；候选只指向反馈事件和推荐主题，不复制评论内容。
5. 数据页新增复核区：展示脱敏样本、推荐主题、主题情绪和原因，并提供确认、忽略、新主题候选三个显式人工动作。

## 验收

- “画面很好但卡顿严重”产生两个主题，画面为正面、性能/网络为负面。
- 超过两个候选主题或并列歧义生成一条待复核候选，刷新后仍可见。
- 确认/忽略只改变候选状态，不改写规则与历史趋势。
- 跨 Workspace 不能读取或操作候选。
- 单元测试覆盖最多两主题、按主题情绪、候选原因和状态机；后端测试与前端构建通过。
