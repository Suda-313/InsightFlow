# P4 业务闭环与权限协作设计

## 目标与范围

P4 将 InsightFlow 从“发现异常并给出只读分析”扩展为“发现、调查、人工确认、处置、复盘”的可追溯闭环。

本期实现以下能力：

- 本地账号、BCrypt 密码与 JWT 登录态；
- 组织成员、工作区成员和最小角色权限；
- 告警触发后的异步调查卡片；
- 人工确认的提案式处置、幂等、审计与撤销；
- 人工纠错沉淀为规则候选、别名或评测样本；
- 日报、周报和版本复盘报告；
- 前端交互审查与收敛。

本期明确不实现飞书、钉钉、Jira 等外部协作集成，也不让 Agent 获得数据库写权限。

## 设计选择

`Alert` 是异常触发时的不可变证据快照，不能承担负责人、处置结论和可撤销状态。因此新增独立的调查与提案实体：告警只负责“发生了什么”，调查卡片负责“证据指向什么”，人工命令负责“决定做什么”。

不引入完整 IAM 平台。认证仅使用 Spring Security、BCrypt 和签名 JWT；授权在服务层集中校验组织、Workspace 和角色，不信任前端传递的用户或角色字段。

## 领域模型与隔离

| 模型 | 职责 | 隔离约束 |
| --- | --- | --- |
| `AppUser` | 本地登录账号，只暴露 `public_id` | 不直接拥有业务数据 |
| `OrganizationMember` | 用户在组织内的角色 | 一个用户可属于多个组织 |
| `WorkspaceMember` | 成员可访问的游戏/产品线 | 每次 Workspace 请求必须验证 |
| `InvestigationCase` | 关联 Alert 的调查卡片 | 必须保存 `workspace_id`，Alert 不可跨 Workspace 引用 |
| `InvestigationEvidence` | 调查时生成的趋势、样本、时间、版本线索快照 | 只读、脱敏、归属调查卡片 |
| `ActionProposal` | 待确认的确认、忽略、合并、分派、关闭建议 | 必须关联调查卡片与 Workspace |
| `ActionExecution` | 已执行命令与撤销关系 | 保存幂等键、操作者和撤销来源 |
| `AuditLog` | 认证、处置、纠错、报告的审计事件 | 保存 Workspace、操作者、目标 public ID 与脱敏摘要 |
| `ManualCorrection` | 人工修正及其沉淀状态 | 只允许授权成员创建和审核 |

所有对外 API 仅使用 UUID `public_id`。所有业务查询和写入都以路径中的 Workspace UUID 解析为内部 `workspace_id` 后再过滤。

## 身份与角色

角色固定为：

- `OWNER`：组织初始化、成员管理、全部 Workspace 管理与撤销；
- `ANALYST`：查看数据、调查、报告、提交纠错，不可执行处置命令；
- `OPERATOR`：在已加入的 Workspace 中确认、忽略、分派、关闭和撤销处置；
- `VIEWER`：只读查看看板、调查与报告。

首个组织 Owner 仅可通过部署环境中的一次性 bootstrap 口令创建；不设置默认密码，也不开放匿名注册。Owner 之后可邀请成员并分配 Workspace。JWT 中仅保存用户公开 ID 和过期时间，实际组织与 Workspace 权限每次从数据库校验，避免角色变更后旧 Token 继续越权。

## 调查与人工处置流程

```text
Alert 触发
  -> 创建幂等的 investigation AsyncTask
  -> 只读 Agent 汇总受控 Tool 证据
  -> InvestigationCase(PENDING_REVIEW) + Evidence
  -> Agent 产生 ActionProposal（不执行）
  -> 有权限的人工预览影响
  -> Command Service 执行 / 拒绝提案
  -> ActionExecution + AuditLog
  -> 可撤销时创建反向执行记录 + AuditLog
```

调查任务复用现有 `AsyncTask` 租约、重试和 Workspace 隔离机制，任务类型为 `investigation`，幂等键为告警公开 ID。Agent 只可调用既有的只读调查 Tool；版本或活动线索仅在已发布知识库中检索，不连接未知外部数据源。

提案只支持 `CONFIRM`、`IGNORE`、`MERGE`、`ASSIGN`、`CLOSE`。预览接口只返回拟变更的公开对象、当前状态和影响数量；命令接口要求 `Idempotency-Key`，并在服务层二次验证角色、成员关系、目标状态和提案归属。

## 纠错、评测与报告

人工纠错覆盖主题、风险等级和调查结论。纠错先形成不可变记录，再由 Owner 审核其沉淀类型：主题别名、规则候选或评测样本。规则和知识库变更发布前自动运行现有通用金标评测与 RAG 专项评测；若质量相对基线退化，拒绝发布并保留可解释的失败原因。

日报、周报和版本复盘仅汇总已确认的调查卡片与已有证据。报告中的每一项结论必须带内部证据链接，不能把模型自由生成内容写成业务事实。报告仍由异步任务生成，不阻塞页面请求。

## 前端体验边界

新增“调查中心”作为调查卡片、提案确认、纠错和复盘入口。首页只保留一张最近待办调查的摘要和跳转链接，不复制完整告警处置列表。权限不足、空数据、任务运行和命令失败均须显式展示，不能用空列表或按钮无响应掩盖失败。

P4 实现后审查现有导航与首页：删除或合并重复入口，移除没有后端行为的按钮，并将 AI 对话中的“查看数据/生成报告”等通用操作引导到已有页面而非新增页面。

## 验收标准

1. 一个 Owner 可创建成员、授予 Workspace 访问并登录；无成员关系的用户不能读取该 Workspace。
2. 告警仅生成一次调查任务；任务失败可诊断，成功后形成带证据的待确认调查卡片。
3. Agent 不能直接改变 Alert、调查或处置状态；只有获得角色授权且携带幂等键的人工命令可执行。
4. 确认、忽略、分派、关闭和撤销均可通过审计记录追溯操作者、时间、目标与来源提案。
5. 人工纠错可进入规则、别名或评测样本的审核流程；质量退化会阻止发布。
6. 三类报告可追溯至已确认调查与证据。
7. 前端仅展示可执行的按钮，所有关键状态都具备加载、空态与失败反馈。
